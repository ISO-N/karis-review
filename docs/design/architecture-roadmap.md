## 1. 执行摘要

Karis Review 已具备一个**架构基础扎实的模块化单体**：依赖单向、领域核心（排期算法）纯函数化、离线优先同步、乐观锁并发控制、传输协议优化，这些是很多同类产品做不好的地方，值得珍惜。

当前系统真正的短板不在"代码结构"，而在**工程化基础设施**：单点部署、备份与主数据同库（故障域重叠）、无可观测性、同步邮件、统计实时聚合、无缓存与限流。这些短板决定了系统**可靠性上限**，而非功能上限。

本文档的战略判断：

1. **继续坚持模块化单体**，不因"大系统"而贸然上微服务——单体不是过渡态，是可长期驻留的目标架构形态；微服务只是按需演进的选项。
2. **把模块边界升级为显式契约**（ArchUnit 固化 + 模块 API 清单），为未来按需拆分预留"手术缝线"。
3. **按 可靠性 → 可扩展性 → 平台化 三阶段演进**，先解决"数据不会丢、故障能恢复"，再谈"水平扩展"。
4. 唯一值得提前布局拆分的上下文是 **Identity（身份）** 与 **Analytics（统计）**，其余业务（Content / Review / Scheduling）在可预见的规模内留在单体。

## 2. 现状架构健康度评估

### 2.1 优势（Strengths）——需要继续维护的资产

| 维度 | 现状 | 评价 |
|------|------|------|
| 模块化 | 11 个业务模块，`controller → service → repository` 单向依赖，严禁循环依赖 | ✅ 模块化单体范式的正确实践 |
| 领域核心 | `SchedulingEngine` 零依赖纯算法类，前后端（Java/Dart）公式一致 | ✅ 核心域抽离干净，可测试、可移植 |
| 离线优先 | Drift/SQLite 本地缓存 + `sync_events` 事件游标增量同步 | ✅ 移动端体验设计正确 |
| 并发控制 | `review_version` 乐观锁 + `PESSIMISTIC_WRITE` | ✅ 跨设备评分冲突处理到位 |
| 传输优化 | gzip + ETag/304 + Protobuf 内容协商 | ✅ 高流量接口优化意识强 |
| Schema 治理 | Flyway 版本化迁移，`ddl-auto=none` | ✅ 变更可审计、可回放 |
| 安全基础 | bcrypt、JWT、验证码防枚举、脱敏操作日志 | ✅ 安全意识良好 |

### 2.2 风险与缺口（Gaps）——按严重度排序

| # | 缺口 | 现状 | 风险等级 |
|---|------|------|---------|
| G1 | **备份与主数据同库** | `backup_snapshots` 与业务表存在同一 PostgreSQL 实例；应用级每日备份与主库故障域完全重叠 | 🔴 高：数据库丢失 = 备份同时丢失 |
| G2 | **单点部署** | backend + postgres 单机，无 HA、无 WAL 归档（无 PITR） | 🔴 高 |
| G3 | **无可观测性** | 无指标（Micrometer/Prometheus）、无结构化日志聚合、无追踪 | 🟠 中高：故障定位靠人工翻日志 |
| G4 | **同步邮件** | `SmtpMailSender` 在请求线程内同步发送，验证码场景拖慢响应，失败影响注册/找回 | 🟠 中 |
| G5 | **统计实时聚合** | overview/trend 每次实时扫描 `review_logs`，数据增长后变慢 | 🟠 中 |
| G6 | **无缓存层** | 卡组列表、统计、ETag 校验数据均直接查库 | 🟠 中 |
| G7 | **无限流/防爬** | 认证接口无速率限制，注册/登录可被脚本轰炸 | 🟠 中 |
| G8 | **Flutter Web 未托管 CDN** | 前端构建产物未纳入生产部署链路 | 🟡 低 |
| G9 | **密钥管理薄弱** | `JWT_SECRET` 等存 `.env.prod`，无轮换机制 | 🟡 低 |
| G10 | **恢复流程未演练** | `BackupService.importData` 先删后导且无事务保护，极端情况留下半删状态 | 🟠 中（高危险操作） |

### 2.3 结论

**架构骨架无需重构**。当前最优先的投资方向是：备份外置与高可用（G1/G2）、可观测性（G3）、异步化（G4）、预聚合（G5/G6）——这些是"可靠性基建"，投入产出比最高。

## 3. 战略建模：限界上下文与子域划分

### 3.1 子域划分

| 子域 | 类型 | 说明 |
|------|------|------|
| 排期引擎（Scheduling） | **核心域 Core** | Stage 0-8 算法、重学插入、逾期惩罚——差异化竞争力 |
| 复习会话与同步（Review） | **核心域 Core** | 会话快照、评分、跨设备同步、冲突解决——体验关键路径 |
| 内容管理（Content：Deck/Card） | 核心域（内容即产品） | 卡组、卡片、富文本、导入、搜索 |
| 身份认证（Identity） | 支撑域 Supporting | 注册/登录/验证码/密码重置/邀请码——必要但非差异化 |
| 统计洞察（Analytics） | 支撑域 Supporting | overview/deck/trend 统计 |
| 备份恢复（Backup） | 支撑域 Supporting | 导出/导入/每日快照 |
| 通知投递（Notification） | **通用域 Generic** | 邮件发送——可外购/可替换，应独立抽象 |
| 审计日志（Audit） | 支撑域 Supporting | user_logs 脱敏操作日志 |

### 3.2 限界上下文与映射

```
┌──────────────────────────────┐
│      Client (Flutter)        │  ← 前端是多上下文的"客户"，通过 API 网关消费
└──────────┬───────────────────┘
           │ HTTPS (JSON / Protobuf)
┌──────────▼───────────────────┐
│   API 网关（阶段一引入）        │  限流 / TLS 终结 / 静态托管 / 鉴权透传
└──────────┬───────────────────┘
           ▼
┌─────────────────────────── 模块化单体（业务边界清晰） ───────────────────────────┐
│                                                                                  │
│  ┌────────────┐    ┌──────────────────┐    ┌────────────────────────────────┐  │
│  │ Identity   │    │ Content          │    │ Review（含 Scheduling/Sync）    │  │
│  │ 认证/验证码 │───►│ Deck/Card/导入/搜索│───►│ 会话/评分/同步/冲突解决          │  │
│  └────────────┘    └──────────────────┘    └────────────────────────────────┘  │
│        ▲                    ▲                          ▲          ▲             │
│        │                    │                          │          │             │
│        │                    │      ┌───────────────────┘          │             │
│  ┌─────┴─────────┐   ┌──────┴───────┐    ┌───────────────────┐    │             │
│  │ Audit 审计日志 │   │ Analytics    │    │ Backup 备份恢复    │    │             │
│  │ (user_logs)   │   │ 统计预聚合    │───►│ 导出/导入/快照外置  │───►│             │
│  └───────────────┘   └──────────────┘    └───────────────────┘    │             │
│                             ▲                    ▲                │             │
│  ┌───────────────┐         │                    │                │             │
│  │ Notification  │─────────┘                    │                │             │
│  │ 邮件(Outbox)  │                              │                │             │
│  └───────────────┘                              └────────────────┘             │
└──────────────────────────────────────────────────────────────────────────────────┘
```

**上下文映射要点：**

- **Identity → 所有**：用户身份是全局共享的（Shared Kernel 的边界控制：只共享 `userId`，不共享内部表）。
- **Content → Review（上游/下游）**：Review 依赖 Deck/Card 数据但只读 `id/stage` 等必需字段——保持 `UUID 外键`而非 JPA 关联对象的现状，这正是防腐层（ACL）的雏形。
- **Scheduling 是 Review 的内嵌核心**：算法与编排同属一个事务边界（评分 = 状态变更 + 排期计算必须原子），**不宜拆为独立服务**——强一致性场景，拆开会引入分布式事务，得不偿失。
- **Analytics ← Review/Content**：统计只消费数据，未来可改为订阅事件流（阶段二）。
- **Backup → 所有**：全量导出者；是唯一被允许横向读取所有上下文的模块。
- **Notification**：当前嵌在 auth 内，战略上属通用域，应独立抽象（邮件服务接口 + Outbox）。

### 3.3 模块契约纪律（Phase 1 落地）

为未来拆分留缝，需把"口头规则"固化为**可验证的机器检查**：

1. **模块 API 清单**：每个模块维护 `MODULE.md`，声明对外暴露的 Service 接口（模块门面），禁止跨模块直接调用对方 Repository / 实体字段。
2. **ArchUnit 规则**（后端单测）：依赖方向、包可见性、禁止跨模块 Repository 引用，纳入 CI。
3. **实体隔离**：跨模块只传递 `UUID + 必需值对象`，不传递 JPA 实体（现状已是如此，需固化）。
4. **同步领域（sync）定位**：sync 不是业务上下文，是 Review 上下文的对外同步协议，阶段二随 Review 保留或下沉为共享协议层。

## 4. 目标架构

### 4.1 架构原则

| 原则 | 含义 |
|------|------|
| P1 演进优先于重构 | 任何变更都是增量式，不推倒重来 |
| P2 模块化单体是长期形态 | 微服务是按需演进的选项，不是默认答案 |
| P3 核心域留在强一致边界内 | 评分/排期/同步保持单体事务，不做分布式拆分 |
| P4 支撑域可独立演进 | Identity/Analytics/Backup 优先获得拆分能力 |
| P5 可逆性 | 每个关键决策记录 ADR，保留回退路径 |
| P6 故障域分离 | 备份、缓存、日志与主数据不共享同一故障点 |

### 4.2 阶段一（当前 → 6 个月）：可靠性基建，夯实模块化单体

**目标：数据不丢、故障能恢复、问题可定位、请求可限流。**

```
                        ┌─────────────────┐
                        │  CDN (Flutter)   │  Web 静态产物
                        └────────┬────────┘
                                 │
┌───────────┐   HTTPS   ┌────────▼────────┐    ┌────────────────┐
│ Flutter   │──────────►│  反向代理网关     │───►│  限流 / TLS    │
│ 客户端     │           │  (Caddy/Nginx)  │    └────────────────┘

┌─────────────────────────────────────────────────────────────┐

│   Backup   │ Audit   │ Notification(Outbox)                │  │
└──────┬──────────────┬──────────────────┬───────────────────┘
       │              │                  │
┌──────▼──────┐ ┌─────▼──────┐   ┌───────▼────────┐
```

**本阶段工作包（对应风险缺口）：**

| 工作包 | 对应缺口 | 关键动作 |
|--------|---------|---------|
| WP-1 备份外置 | G1/G10 | `backup_snapshots` 快照改为上传对象存储（MinIO/S3/云 OSS）；保留最近 N 份；导入操作改造为"事务内导入 + 失败回滚 + 导入前自动快照" |
| WP-2 数据库高可用与 PITR | G2 | WAL 归档到对象存储；`pg_basebackup` 定期基础备份；配置只读副本（读写分离可延后）；备份恢复演练纳入 CI 流程（季度级演练） |
| WP-3 可观测性 | G3 | 引入 Micrometer + actuator，暴露 `/actuator/prometheus`；JVM/HTTP/DB 指标；日志输出 JSON 结构化，聚合到 Loki/Grafana；阶段一暂缓分布式追踪 |
| WP-4 邮件异步化 | G4 | 发送请求写入 `outbox` 表 + 定时 worker 投递，支持重试与死信；接口不再同步依赖 SMTP 结果 |
| WP-5 统计预聚合 | G5/G6 | 新增日级预聚合表 `daily_review_stats`（user × day × deck 维度）；trend/overview 改查预聚合；Redis 缓存卡组列表与统计（失效策略：写后失效） |
| WP-6 限流与网关 | G7 | 网关层按 IP 限流（登录/注册/发码接口严格限流）；应用层按用户限流（Bucket4j）；TLS 终结与 HTTP/2 |
| WP-7 前端托管 | G8 | Flutter Web 产物发布到 CDN/对象存储，与 API 分离域名；缓存策略（index.html 短缓存，assets 长缓存） |
| WP-8 密钥管理 | G9 | JWT 支持多密钥（kid 轮换）；密钥从环境变量迁移到可轮换的存储；`JWT_SECRET` 轮换流程文档化 |
| WP-9 模块契约固化 | — | 模块 API 清单 + ArchUnit 依赖规则 + 实体隔离检查，全部纳入 CI |

**技术选型建议（保持轻量）：** Caddy（网关/自动 HTTPS）· Prometheus + Grafana + Loki（可观测性）· Redis（缓存，单实例起步）· MinIO 或云 OSS（对象存储）· Bucket4j（限流）· ArchUnit（架构测试）。

### 4.3 阶段二（6 → 18 个月）：按需拆分，水平扩展

**触发条件（满足其一才启动拆分）：** 用户量级进入十万级 / Identity 或 Analytics 出现独立扩缩容需求 / 团队扩展到可维护多服务的规模。

**拆分策略（只拆该拆的）：**

```
                    ┌─────────────────────────┐
                    │   API 网关（限流/路由/鉴权透传）  │
                    └──────┬─────────┬────────┘
                           │         │
              ┌────────────▼──┐   ┌──▼──────────────────┐
              │ Identity 服务  │   │  Analytics 服务       │
              │ 认证/验证码/用户 │   │ 统计预聚合/趋势/洞察    │
              │ (独立扩容, 事件: │   │ (订阅事件流, 读多写少)  │
              │  UserCreated)  │   └──────────────────────┘
              └────────────┬──┘
                           │ 事件流
              ┌────────────▼───────────────────────────────┐
              │  核心单体（仍为单体，可水平多副本）              │
              │  Content │ Review + Scheduling + Sync      │
              │  Backup │ Audit                            │
              └────────────────────────────────────────────┘
```

- **Identity 拆分**：认证流量与业务流量隔离，独立扩缩容；用户数据通过事件（`UserCreated`/`UserUpdated`）发布给消费方。
- **Analytics 拆分**：改为**事件驱动**——核心单体在业务事务内写 Outbox，Analytics 消费事件流做预聚合；彻底解除 Stats 对核心库的实时查询。
- **同步机制演进**：`sync_events` 数据库触发器在单体内部仍可用；一旦引入跨服务写（如 Identity 拆出后用户变更），触发器无法捕获跨库事件 → **Outbox 模式**（业务表事务内写 outbox → 发布到消息队列 NATS/Kafka）成为标准事件通道。
- **Content 拆分（可选）**：仅当卡片量级与检索需求明确超过单体能力（如全文检索、海量媒体）才拆，并配独立搜索索引（PostgreSQL FTS / Meilisearch）。
- **Review 不拆**：评分 + 排期 + 冲突解决是强一致事务，拆分的代价（分布式事务/最终一致性）远大于收益。

### 4.4 阶段三（18 个月+）：平台化

仅在业务验证多产品 / 社区 / 生态需求时启动：

1. **共享平台服务**：Identity 升级为统一账号平台（多产品 SSO），Analytics 升级为跨产品数据洞察平台。
2. **开放 API**：若做第三方集成/社区共享卡组，提供带配额管理的开放 API（网关 + API Key）。
3. **内容市场**：卡组模板市场（Content 上下文增加发布/订阅关系模型，引入 `DeckShare`/`DeckTemplate` 实体）。
4. **多租户准备**：若做团队/组织版，`user_id` 维度升级为 `org_id + user_id`，涉及全部数据模型，需提前在阶段一评估（不预埋，按 YAGNI 原则）。

## 5. 关键技术决策（ADR）

> 完整 ADR 应作为独立文件归档到 `docs/adr/`（每个决策一个文件）。此处给出决策摘要与理由。

### ADR-001：保持模块化单体，不采用微服务起步

- **状态**：已接受（现状即此决策的产物，本 ADR 将其显式化）
- **Context**：团队规模小、产品早期、领域边界仍在随需求演进；现有模块化单体已具备清晰的模块边界与单向依赖。
- **决策**：以模块化单体作为长期目标架构；模块边界升级为显式契约（ArchUnit + 模块 API 清单）；仅在 ADR-002 的触发条件下拆分。
- **后果**：+ 迭代快、部署简单、事务一致；− 需要依赖纪律维持边界；− 独立扩缩容受限。

### ADR-002：Identity / Analytics 是优先拆分候选

- **状态**：已接受
- **Context**：认证流量特征（高频、突发）与业务流量差异大；统计查询是纯读且数据可异步化。
- **决策**：阶段二优先拆 Identity 与 Analytics；Review/Content 留在核心单体。
- **后果**：+ 独立扩缩容；+ Analytics 解耦后核心库负载下降；− 引入跨服务通信与事件流基础设施。

### ADR-003：排期算法双端实现，共享测试向量

- **状态**：已接受（现状如此，予以确认）
- **Context**：离线评分需要本地排期，前后端必须行为一致。
- **决策**：Java/Dart 各维护一份公式相同的引擎，用同一组测试向量（含逾期惩罚边界用例）双端验证；算法参数（Stage 间隔等）版本化。
- **后果**：+ 离线体验完整；− 算法变更需双端同步修改，测试向量是唯一防线。

### ADR-004：Review 评分链路的强一致性边界

- **状态**：已接受
- **Context**：评分 = 状态变更 + 排期计算 + 队列插入，必须原子；跨设备冲突靠乐观锁解决。
- **决策**：Review 的评分/同步/冲突解决**永不分拆为独立服务**；跨设备一致性通过 `review_version` 乐观锁保持。
- **后果**：+ 无分布式事务；+ 一致性逻辑简单可推理；− 单点事务吞吐受限于单库（通过读副本与缓存缓解读压力）。

### ADR-005：备份数据与主数据库故障域分离

- **状态**：已接受（阶段一落地）
- **Context**：`backup_snapshots` 与业务数据同库，主库故障则备份同时丢失。
- **决策**：应用级快照外置到对象存储；数据库启用 WAL 归档支持 PITR；导入操作改为事务内执行 + 失败回滚。
- **后果**：+ 恢复能力质变（可恢复到任意时间点）；+ 导入不再破坏性；− 引入对象存储运维与成本。

### ADR-006：邮件投递异步化（Outbox 模式）

- **状态**：已接受（阶段一落地）
- **Context**：同步发信拖慢认证接口，SMTP 故障直接导致注册/找回失败。
- **决策**：验证码/重置邮件写入 `outbox` 表（与业务同事务），后台 worker 投递，重试 + 死信。
- **后果**：+ 接口响应快、失败可重试；− 邮件延迟数秒（可接受）；− 需处理死信告警。

### ADR-007：统计预聚合（日级汇总）

- **状态**：已接受（阶段一落地）
- **Context**：`review_logs` 无限增长，实时聚合查询随数据量线性变慢。
- **决策**：新增日级预聚合表（user × day × deck），趋势/概览查询改查预聚合；实时性从"即时"降为"日级"（当日数据可在当日晚间任务后呈现完整）。
- **后果**：+ 查询耗时稳定；+ 统计模块可独立演进为 Analytics 服务；− 当日统计有延迟（按产品可接受）。

## 6. 质量属性与权衡

| 质量属性 | 目标 | 关键手段 | 权衡取舍 |
|---------|------|---------|---------|
| 可扩展性 | 万级用户单副本可承载，十万级靠水平扩展 | 网关 + 多副本 + 读副本 + 缓存 + 预聚合 | 拆服务增加运维复杂度，故按需拆 |
| 可靠性 | RTO ≤ 1h，RPO ≤ 5min（PITR） | WAL 归档 + 对象存储快照 + 恢复演练 | 对象存储与归档成本 |
| 可维护性 | 新成员 1 周内可上手 | 模块契约 + ArchUnit + ADR + 文档同步 | 架构测试增加 CI 时间（可忽略） |
| 可观测性 | 故障定位 ≤ 10min | 指标 + 结构化日志 + 告警规则 | 基础组件运维负担 |
| 性能 | API 95 分位 < 500ms（现状达标） | 缓存 + 预聚合 + Protobuf + CDN | 缓存一致性策略需维护 |
| 安全性 | 防爆破/防爬/密钥可轮换 | 网关限流 + Bucket4j + kid 轮换 | 限流阈值需调参，误伤风险 |
| 一致性 | Review 强一致，统计最终一致 | 乐观锁 + 预聚合日级 | 统计当日延迟 |

**明确的取舍声明：**

1. **统计时效性（即时 → 日级）**：用统计"晚一天看到"换取"永远快速"。对闪卡产品，趋势数据按日粒度完全够用。
2. **Review 强一致 vs Analytics 最终一致**：核心链路上不妥协强一致；分析类数据接受最终一致。
3. **单体 vs 微服务**：接受"单体内所有模块同生共死"的部署粒度，换取更低的运维与分布式复杂度；用模块契约保留未来的手术能力。

**里程碑验收标准：**

- **M1**：生产环境可查询任意接口的 P95/P99、DB 慢查询、JVM 指标；告警可通知到人。
- **M2**：恢复演练手册可执行（对象存储快照 → 全新环境恢复）；`import` 接口在失败时可回滚，导入前自动快照。
- **M3**：发码/重置接口响应不再依赖 SMTP；投递失败有重试与告警。

- **M5**：任一 backend 实例或主库宕机，服务不中断或 10 分钟内恢复。
- **M6-M8**：Identity/Analytics 独立部署与扩缩容；业务单体无感知。

## 8. 风险与应对

| 风险 | 可能性 | 影响 | 应对 |
|------|--------|------|------|
| 备份恢复未演练，真出事时恢复不了 | 中 | 灾难性 | 每季度一次恢复演练；演练流程文档化；导入操作前置快照 |
| 模块边界随时间腐化 | 中 | 拆分困难 | ArchUnit 入 CI，模块 API 清单评审纳入 Code Review |
| 统计预聚合口径与实时不一致 | 中 | 数据可信度受损 | 预聚合由 `review_logs` 幂等重算（按日全量重建），口径与实时查询对齐测试 |
| 排期算法双端漂移 | 中 | 跨设备排期不一致 | 共享测试向量 + 双端 CI 跑同一用例集；算法变更必须双端同步 |
| 拆服务后数据一致性失控 | 低 | 严重 | 坚持"强一致留在单体"原则；跨服务只传事件与 ID |
| JWT 泄露 | 低 | 严重 | kid 多密钥 + 定期轮换 + 登录审计 + 必要时 Token 黑名单（阶段二） |

## 9. 首批落地建议（30 天行动清单）

按优先级排序，可直接进入排期：

1. **P0 · 备份外置**：把 `backup_snapshots` 的写入改为"对象存储 + 库内元数据表"（或最小改动：快照 JSON 落盘到独立存储卷并异地备份）。这是当前系统最大的故障隐患。
2. **P0 · 导入安全**：`BackupService.importData` 改为事务内"导入 → 校验 → 提交"，失败自动回滚；导入前强制自动快照。
3. **P1 · 可观测性基线**：加 Micrometer + actuator + prometheus 依赖，暴露指标；日志切 JSON 格式。
4. **P1 · 网关前置**：Caddy 反向代理 + 自动 HTTPS + 登录/注册/发码限流；Flutter Web 产物接入托管。
5. **P2 · 邮件异步**：Outbox 表 + 定时 worker（最小实现可先用 `@Async` + 重试过渡）。
6. **P2 · 模块契约**：ArchUnit 依赖规则 + 首批模块 API 清单（建议从 `review` 与 `backup` 开始）。
7. **P3 · 统计预聚合 + Redis 缓存**：`daily_review_stats` 表 + 晚间重算任务 + 卡组列表缓存。
